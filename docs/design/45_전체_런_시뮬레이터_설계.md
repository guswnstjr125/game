# 다크 레기온 — 전체 런 시뮬레이터 설계 (J77)

> **상태**: 전체 런 기준 정책은 `01` D-86으로 확정. 선택별 세부 우선순위·동점 처리, 표본 확장 및 통계 판정은 구현 전에 명시한다.
> **기준**: PR #118의 2차 MVP 준비 설계, main `e8d0acb`, `01` §7 D-04·D-11·D-34·D-53·D-62·D-66·D-69·D-73·D-75~D-80.
> **정본**: 전투는 `15`, 밸런스 지표는 `16` §8, 런 진행은 `03`·`14`·`24`·`26`·`32`. 이 문서는 D-86을 풀어서 설명하며 기존 게임 규칙이나 D 결정을 대체하지 않는다.

## 1. 목적과 범위

`15_Battle_Simulator_설계.md`의 `BattleRunner`는 덱 하나와 Encounter 하나를 실행한다. D-04는 전투 승률을 곱해 런 클리어율을 추정하지 말고, 시드가 충분한 **실제 런**에서 30~45%를 측정하도록 정한다. `32` BAL-02도 런 단위 리포트를 요구한다.

이 설계는 `RunState` 한 개를 시작해 맵 노드를 순서대로 5층까지 직접 진행하는 헤드리스 런 조정기를 제안한다. 전투·보상·이벤트 등은 실제 Core 규칙을 호출하고, 봇은 플레이어 입력을 공급한다. 시뮬레이션과 실제 런의 결과 차이를 막기 위해 규칙을 별도 복제하지 않는다.

포함: 5층×9노드, 전투와 전투 보상, 이벤트·강제 전투, 휴식, 상점, 융합 성소, 클래스/메타 시작 상태, 층 전환·최종 정산, 재현 가능한 로그 및 통계.

제외: Unity 화면/연출, 수치 밸런스 변경, 별도 경로 맵, 실제 플레이어 행동 분포를 사실처럼 가정하는 것, 전투 승률 독립곱 추정.

## 2. 권장 구조

```text
RunSimulationConfig
  ├─ ContentSnapshot (GameDataLoadResult, 정본 Excel에서 만든 동일 데이터)
  ├─ MetaSnapshot (초기 화폐·언락·누적 해금 상태)
  ├─ StartClass × BotPolicy × SeedRange
  └─ RunSimulator
       ├─ RunFactory       → RunState (Stage1Build=false, LastFloor=5)
       ├─ NodeScheduler    → RunMap.KindOf / RunFlow
       ├─ BattleAdapter    → RunBattle / BattleContext / TurnFlow / BotPolicy
       ├─ ChoicePolicies   → 카드·보상·이벤트·휴식·상점·융합 선택
       ├─ MetaSettlement   → 26·41 규칙에 따른 런 종료 반영
       └─ RunResultWriter → 원시 JSONL + 요약 JSON
```

`RunSimulator`는 `RunMapSession` 화면 수명주기를 호출하지 않는다. 해당 세션은 화면 연결 책임을 갖는다. 런 조정기는 같은 Core 데이터와 전이 함수를 직접 사용하며 화면 프레임·Unity 입력에 의존하지 않는다.

## 3. 한 런의 실행 순서

### 3.1 시작

1. 설정에서 `StartClass`, 고정 메타 스냅샷, 봇 정책 버전, `RunSeed`를 읽는다.
2. `18`·`04_밸런스_테이블.xlsx`의 해당 클래스 시작 덱·시작 유물·HP·Crystal·Gold를 사용해 `RunState`를 만든다. 카드·적·콘텐츠 데이터는 기존 `GameDataLoadResult`를 사용한다.
3. 2차 실행은 `Stage1Build=false`, `LastFloor=5`를 둔다. 시작 클래스가 해당 메타 스냅샷에서 잠겨 있으면 그 조합을 실행하지 않고 `invalid_scenario`로 기록한다.
4. 희생 안내는 신규 사용자의 1회성 튜토리얼이라 밸런스 런 기본값에서 끈다. 필요하면 별도 튜토리얼 비교 시나리오로 분리한다 (D-32·D-76).

### 3.2 노드 루프

현재 층의 1~9번 노드를 `RunMap.KindOf(floor,node,false)`로 결정한다. 노드 처리와 노드 완료는 분리한다. 보상·이벤트·휴식·상점의 확정 처리가 끝난 뒤에만 `RunFlow.CompleteNode`를 호출한다.

|---|---|---|
| 일반·정예·보스 전투 | `RunBattle.Start`, `BattleContext`, `EncounterFactory`, `TurnFlow`, `BattleRandom`; 적 편성·Wave·보스 패턴은 `03`·정본 데이터 | 봇이 합법적인 입력을 고르고 전투를 끝까지 진행한다. 플레이어 HP 0 또는 노드 30턴 제한 패배는 실제 런 패배로 기록한다. 배틀별 결과를 런에 누적한다 |

### 3.3 맵 경로와 3층 노드 3

D-11에서 맵은 단일 경로로 고정되어 있으므로 경로 선택 봇은 없다. 봇은 현재 노드에서 다음 노드로 진행한다. 3층 노드 3의 이벤트/융합 성소는 `03` §5의 50% 난수 추첨이며, 성소를 골라 방문하는 선택이 아니다. 상점은 2~5층 노드 6에 한 번씩, 총 최대 4회 등장한다 (D-34).

## 4. 봇 정책 대안

기준 정책은 `01` D-86으로 확정했다. 전투는 `15` §3 Greedy 우선순위를, 카드·보상·이벤트·휴식·상점·융합은 규칙 기반 우선순위를 사용한다. 모든 정책은 `BotPolicyId`와 버전이 있는 함수이며 같은 정책·설정·시드에서 결과가 같아야 한다. 규칙 기반 기준선의 결과만 기본 BAL-02 리포트에 넣고, 대안은 별도 비교 실험으로 분리한다. 어떤 봇 정책의 결과도 플레이어의 실제 클리어율이라고 표현하지 않는다.

| 결정 | 기준 정책 (D-86) | 비교 대안 | 장점 | 한계/위험 |
|---|---|---|---|---|
| 전투 입력 | `15` §3의 생존 → 처치 가능 → Lv3 소환 → 희생/Crystal → 기본 공격 카드 | 균등 무작위, 전술 휴리스틱 | 기존 Battle Simulator와 같은 명시 우선순위로 런 간 비교 가능 | Greedy 결과는 사람 플레이 실력 추정치가 아니다 |
| 카드·보상 | Core가 생성한 유효 후보에서 규칙 기반 우선순위 선택. 카드 건너뛰기는 D-37 허용 규칙을 적용 | 즉시 효율, 덱 시너지, 희귀도, 무작위 선택을 별도 정책 버전으로 비교 | 선택 기준을 정책 파일/로그로 추적 가능 | 세부 우선순위·동점 처리는 구현 계약에서 정해야 한다 |
| 이벤트 | 선택 가능한 옵션 중 규칙 기반 우선순위 선택. 효과와 난수는 `EventFlow`·D 정본 사용 | 생존 우선, 장기 자원 가치, 무작위 선택을 별도 버전으로 비교 | 기존 효과를 그대로 호출 | 옵션 평가 순서는 정책 버전으로 고정한다 |
| 휴식 | 사용 가능한 회복/강화 중 규칙 기반 우선순위 선택, `RestFlow` 유효성 유지 | 회복 우선, 강화 가치 우선, HP 기준 변형 | 생존/성장 성향을 비교 가능 | 수치 threshold를 새 게임 규칙으로 만들지 않는다 |
| 상점 | 구매·제거·보류를 규칙 기반으로 선택하고 D-62 재고·가격·제한을 적용 | 생존/시너지 구매, 골드 보유, 제한 예산 변형 | 경제 사용량을 측정 가능 | 선택 점수는 정책 버전별로 드러낸다 |
| 융합 | 유효 재료·레시피 중 규칙 기반 우선순위 선택, `FusionSystem` 비용·충전 적용 | 고정 레시피 우선, 충전 보존, 파워 평가 변형 | 기존 융합 규칙을 사용 | 선택 점수·동점 규칙은 구현 전에 명시한다 |
| 경로 | D-11의 단일 경로 진행. 봇 결정 없음 | 해당 없음 | 모든 런이 같은 맵 구조를 따름 | 3층 노드 3 이벤트/성소는 정본 난수 추첨이다 |

비교 대안은 기준선과 섞지 않고 별도 실험으로 실행한다. 대안 실행 시 정책 ID·버전·선택 trace를 독립 기록한다. 규칙 기반의 개별 선택 순서나 동점 처리 방식이 기존 정본에 없으면 임의로 확정하지 않고 구현 명세에 버전으로 기록한다.

## 5. 초기 메타·해금 상태별 측정

`01` D-86에 따라 M0·M1·M2를 서로 독립된 실험 집합으로 측정한다. 한 시나리오의 시작 메타 스냅샷은 반복 런마다 초기화한다. 표본 간 화폐·언락을 넘기지 않으며 순차 누적 진행 M3는 J77 기준 결과에서 제외한다.

| 프로필 후보 | 시작 상태 | 측정 목적 | 해석 제한 |
|---|---|---|---|
| M0 새 저장 | NEC 시작 가능, Rare/Legendary 카드 풀 잠김, 새 저장 기본값 | 신규 계정 기준 결과. 가능한 `snapshot × class` 조합별 1,000런 | 잠긴 클래스 조합은 실행하지 않고 제외 이유 기록. 현재 NEC 시작 가능 |
| M1 해금 단계 스냅샷 | D-53의 각 해금 진행 단계를 별도 고정 fixture로 명시. 각 snapshot ID와 시작 가능 클래스 목록 기록 | 해금 진행 상태별 결과. 각 `snapshot × class` 조합별 1,000런 | 서로 다른 M1 snapshot을 한 메타 상태처럼 섞지 않고 각각 보고 |
| M2 풀 언락 밸런스 | 모든 클래스와 Rare/Legendary 풀을 연 명시적 저장 fixture | **클래스 간 비교의 기준선**. 각 클래스 1,000런 | 인공 저장이므로 신규 계정 진행을 대표하지 않음 |

M0, 각 M1 snapshot, M2를 별도 보고한다. M2의 클래스별 클리어율을 먼저 제시하고 M2 집계는 보조 표시한다. 전체 집계는 각 메타 snapshot 안에서 가능한 클래스 결과만 합산한다. 서로 다른 M1 snapshot 및 M0·M1·M2를 서로 합산하지 않는다.

## 6. 시드·반복·재현

### 6.1 난수 원칙

- 런 시드는 `RunState.RngSeed`의 `long` 값을 그대로 기록한다. `double` 변환·부동소수 문자열을 사용하지 않는다.
- 기존 `Seeds.NodeSeed(RngSeed, Floor, StageIndex)`, `Seeds.RewardSeed(NodeSeed)`, `BattleRandom`을 게임 난수에 사용한다. 엘리트 편성·Wave 2·셔플, 보상·이벤트의 기존 난수 순서를 바꾸지 않는다 (D-69·D-73·D-75·D-77).
- 각 반복 런의 `RunSeed`와 게임 난수 스트림 및 봇 정책 난수 스트림은 분리한다. 스트림은 시드와 식별자를 사용한 결정적 파생으로 재구성하며, 한 스트림 소비량이 다른 스트림의 상태를 이동시키지 않는다. 인덱스별 파생은 실행 순서·병렬 처리에 의존하지 않는다. 기존 Core 게임 난수 경로는 바꾸지 않는다.
- 런 레코드에는 BaseSeed, RunIndex, 정확한 `RunSeed`, 게임/정책 스트림 ID·버전, policy version, data/meta snapshot hash를 기록한다. 정확한 stream seed 파생 함수는 구현 계약에 이름·버전을 고정하고 재현 테스트로 검증한다.
- 같은 `RunSeed`라도 봇 정책 버전·ContentSnapshot·MetaSnapshot이 다르면 별도 결과다. 모든 설정에 해시를 기록한다.

### 6.2 반복 수

초기 실행은 각 유효한 메타 snapshot × 시작 클래스 조합당 **1,000런**이다 (D-86). `attempted_runs=1000`을 보고하고, 오류는 유효 승패에서 분리해 `valid_game_runs`와 `simulation_errors`로 나눈다. 추가 배치의 조건·최대 표본 수·신뢰구간·D-04 경계 판정은 아직 확정하지 않았다. 정책 비교 실험은 기준선 결과와 분리하고, paired seed를 사용하면 그 사실을 명시한다.

### 6.3 재현 로그

원시 런 레코드(JSONL 한 줄/런) 후보 필드:

```json
{
  "schema_version": 1,
  "source_commit": "<git sha>",
  "data_snapshot_hash": "<export/content hash>",
  "scenario_id": "M2-ELE-RULE-PRIORITY-v1",
  "policy_id": "RULE-PRIORITY-v1",
  "meta_snapshot_hash": "<canonical snapshot hash>",
  "base_seed": "<decimal long>",
  "run_index": 17,
  "run_seed": "<decimal long>",
  "game_rng_stream": "CORE_GAME-v1",
  "policy_rng_stream": "BOT_POLICY-v1",
  "start_class": "ELE",
  "outcome": "Defeat",
  "death_floor": 4,
  "highest_floor_cleared": 3,
  "nodes_completed": 27,
  "battle_count": 12,
  "total_turns": 61,
  "hp_lost_by_node": [],
  "choice_trace": [],
  "simulation_error_code": null
}
```

선택 추적은 결정 입력과 결과 ID만 기록한다(선택한 카드·이벤트 옵션·구매·강화 인스턴스·융합 재료). 원시 전체 전투 객체를 로그로 저장하지 않는다. 요약 JSON에는 실행 설정·유효/무효 표본·승/패·신뢰구간·실행 버전·분포 지표를 넣는다. 한 레코드로 `RunSeed`와 설정을 복원해 같은 노드를 재생할 수 있어야 한다.

## 7. 결과 지표

| 지표 | 정의 | 필수 분할 |
|---|---|---|
| `run_clear_rate` (1차) | `Victory / (Victory + Defeat)`. 실제 5층 보스 및 최종 보상 완료에서만 승리. `simulation_error`는 분모와 패배 수에서 제외하고 별도 보고 (D-86) | MetaSnapshot × StartClass × 기준 BotPolicy |
| `floor_reach_rate[f]` | 층 f의 노드 1을 시작한 런 / 유효 시작 런 | 위 분할 + 층 |
| `floor_clear_rate[f]` | 층 f 보스 처치·보상 확정까지 끝난 런 / 유효 시작 런 | 위 분할 + 층 |
| `death_floor_distribution` | 패배가 처음 확정된 층과 노드의 건수·비율 | 위 분할 + 층/노드 |
| `nodes_completed` | 정상 확정 완료된 노드 수 (0~45) | 분포·중앙값·평균 |
| `hp_remaining` | 런 종료 시 잔여 HP; 승리·패배·포기 구분 | 평균·중앙값·분위수 |
| `hp_lost_by_kind` | `16` D-14 방식으로 전투 중 손실 집계. 이벤트 회복 등은 별도 칸 | 일반/정예/보스, 층, 강제 전투 별도 |
| `gold_flow` | 전투/이벤트/층 보상 획득 및 상점 소비 | 층, 이벤트, 구매 타입 |
| `card/relic/fusion_usage` | 획득·보유·선택·융합 및 카드별 사용 기여 | Class·Policy·Floor |
| `simulation_error_rate` | 잘못된 데이터·정의되지 않은 선택·watchdog 등 게임 규칙 패배가 아닌 실행 오류 비율 | 코드·노드·데이터 ID |

패배·30턴 제한 패배는 유효한 게임 결과다. 예외, 누락 데이터, 시뮬레이터 watchdog은 `simulation_error`로 따로 집계하고 게임 패배로 위장하지 않는다. 오류 표본을 제외한 유효 표본 수와 오류율을 반드시 같이 보고한다. D-04의 `<30%`·`>45%` 경고는 유지하고, CI 구간의 경계 처리 방법은 정해지지 않았다.

### 7.1 결과 보고 형식

각 메타 시나리오를 별도 표로 만든다. M1은 각 `snapshot_id`를 독립 표로 출력한다. 시작 클래스별 결과를 먼저 표시하고, 마지막에 해당 메타 스냅샷에서 실행 가능한 클래스 결과만 합친 집계를 둔다. 서로 다른 스냅샷이나 M0·M1·M2를 합치는 교차 프로필 집계는 만들지 않는다.

| MetaProfile | SnapshotId | Class | Eligible | Attempted | ValidGameRuns | ClearCount | ClearRate | FloorReach/Clear 1~5 | DeathFloor/Node | SimulationErrors | ErrorRate |
|---|---|---|---:|---:|---:|---:|---:|---|---|---:|---:|
| M2 | ALL_UNLOCKED | NEC | Y | 1,000 | 1,000 | — | — | 층별 건수/비율 | 층·노드별 건수/비율 | 0 | 0% |
| M2 | ALL_UNLOCKED | ELE | Y | 1,000 | 1,000 | — | — | 층별 건수/비율 | 층·노드별 건수/비율 | 0 | 0% |
| M2 | ALL_UNLOCKED | 프로필 합계 | — | — | — | — | 합산 계산 | 층별 합산 | 층·노드별 합산 | 합산 | 합산 계산 |

각 셀은 `Attempted=1,000`, `ValidGameRuns=Victory+Defeat`, `SimulationErrors=Attempted-ValidGameRuns`를 만족해야 한다. `ClearRate=ClearCount/ValidGameRuns`, `ErrorRate=SimulationErrors/Attempted`이다. 유효 승패가 0이면 `ClearRate=N/A`로 표시한다. snapshot 집계도 원시 건수를 먼저 합산한 뒤 비율을 계산한다. M0·M1·M2 교차 집계는 만들지 않으며, 클래스 비교는 M2의 클래스별 행을 사용한다. 예시의 결과 칸 대시는 실제 측정 후 값으로 채운다.

## 9. 구현 단위와 자동 테스트 기준

구현은 설계 선택을 승인한 뒤 별도 이슈/PR로 나눈다. 이 문서에서는 게임 코드를 변경하지 않는다.

| 순서 | 작업 단위 | 자동 테스트 기준 |
|---|---|---|
| 1 | `RunScenario`·`MetaSnapshot`·클래스 초기 상태 팩토리 | 시작 덱/유물/HP·Crystal·Gold가 `18`·`04`와 일치, 잠긴 클래스는 `invalid_scenario`, 각 시나리오가 독립된 메타 복사본 사용 |
| 2 | `RunSimulator` 노드 조정기와 결과 코드 | 45노드 성공 fixture, 각 층 경계, 2층 후 최종승리 아님, 5층 최종 보상 후 승리, 노드/보상 중복 확정 없음 |
| 3 | `BattleRunner`·전투 `BotPolicy` | 일반/정예/보스/강제 전투 결과·HP 손실·30턴 패배, 동일 seed 재실행 결과 같음, timeout은 별도 오류 코드 |
| 4 | 보상·이벤트·휴식 선택 Adapter | 선택 가능성·비용·효과·건너뛰기·Rest ContinueOnly, 영혼 감옥 패배·승리 분기, 후보 및 결과 ID 고정 |
| 5 | 상점·융합 성소·Fusion 정책 연결 | 같은 시드 같은 진열, 부족 골드·소모품 최대 3·제거 런당 2회, 무료 성소 융합 1회 제한·저장된 결과 복원 |
| 6 | 메타 프로필·정산 Adapter | M0/M1/M2 fixture별 잠금/풀, 유효 조합별 초기 1,000런, 런 종료 메타 지급, 동일 RunId 중복 정산 방지, trial 간 화폐/언락 누출 없음 |
| 7 | 배치 실행·로그·통계 | 같은 scenario/seed/policy/version에서 핵심 결과 일치, 병렬/순차 결과 일치, raw log 재현, RNG stream 분리, 오류 분모 분리 |
| 8 | BAL-02·BAL-03 통합 검증 | 실제 전체 런 1,000회로 clear rate 계산, 전투 승률 곱을 사용하지 않음, M0·M1 snapshot·M2 독립 보고, M2 클래스별 결과 우선, 오류를 패배와 분리 |

필수 재현성 회귀: 같은 64비트 `RunSeed`, 게임/정책 난수 스트림 버전, 데이터 snapshot, MetaSnapshot, BotPolicy 버전의 런을 두 번 실행하고 모든 노드·선택·전투 결과·정산·최종 지표가 일치해야 한다. 한 스트림에서 난수를 추가 소비해도 다른 스트림의 결과는 바뀌지 않는다. 64비트 큰 시드는 JSON 숫자 정밀도 손실 없이 직렬화한다. 각 실패에는 seed·scenario·node·policy를 출력한다.

## 10. 정책 결정 대기 목록

`01` D-86에서 기준 봇 계열, 단일 경로 적용, M0·M1·M2의 분리 측정, M2 클래스 비교, 클래스 우선 보고, 셀당 첫 1,000런, 난수 스트림 격리 및 오류 분류를 확정했다. 이 범위의 정책 선택은 더 이상 미결정이 아니다.

구현 전 문서화할 세부 사항:

1. 규칙 기반 카드·보상·이벤트·휴식·상점·융합 선택의 정확한 우선순위와 동점 처리. 기존 정본에 없는 부분은 정책 버전이 있는 구현 명세로 정의한다.
2. `RunSeed`에서 실행 인덱스·게임 RNG·정책 RNG 스트림 시드를 만드는 정확한 결정적 파생식과 버전.
3. M1에 포함할 D-53 언락 단계별 `snapshot_id`와 각 스냅샷에서 실행 가능한 시작 클래스 목록.
4. 첫 1,000런 이후 추가 실행 조건, 최대 표본 수, 신뢰구간 및 D-04 경계 판정 방법.
5. 무작위·전술 휴리스틱 등 비기준 정책의 비교 범위와 실행 시점. 이들은 필수 기준선 결과에 섞지 않는다.

기준 정책 결정은 완료됐지만, 실제 런 시뮬레이터가 구현되고 검증되기 전까지는 D-04 목표 달성 여부를 자동 측정했다고 보고하지 않는다. D-04의 30~45%, D-14 HP 손실, D-81의 수치 보류는 이 설계로 변경되지 않는다.
