# 다크 레기온 — 데이터 임포트 매핑 (Excel → JSON → ScriptableObject)

> **정본 결정**: `01` §7 D-39(엔진·데이터 경로), **D-40**(내보내기 방식), D-41(언어)
> **구현 이슈**: #35 (`31` #17 Excel → ScriptableObject 임포터, 1단계 1~2주차)
> 이 문서는 정본 Excel의 어느 시트·열이 엔진의 어느 데이터로 가는지 정한다. 값 자체의 정본은 Excel이다 (`01` §3).

---

## 1. 흐름 (D-40)

```
docs/design/*.xlsx (정본, 사람이 고침)
  │  python3 tools/export_game_data.py        ← 저장소 루트에서 실행
  ▼
DarkLegion/DesignData/<Sheet>.json (생성물, 커밋함, 손으로 고치지 않음)
  │  Unity 메뉴 DarkLegion/Import Design Data  ← 에디터 임포터 (Scripts/Editor/Importers/)
  ▼
DarkLegion/Assets/_Project/Data/Generated/**/*.asset (ScriptableObject, 커밋함, 손으로 고치지 않음)
  │  RuntimeFactory (`08`)
  ▼
Runtime 객체
```

| 단계 | 담당 | 규칙 |
|---|---|---|
| Excel → JSON | `tools/export_game_data.py` | §2 규칙. `--check`는 JSON이 Excel과 다르면 exit 1. `check_design.py`가 0 failed일 때만 내보낸다. `--out DIR`로 다른 폴더에 쓸 수 있다. `DarkLegion/`은 #34에서 Unity 프로젝트를 만든 뒤 처음 내보낸다 (빈 폴더가 아니면 Unity Hub가 새 프로젝트를 만들지 않는다). 그 전에는 기본 `--check`가 `27 file(s) differ`(exit 1)로 나오는 것이 정상이다. #34 전에 검사할 때는 `--out <임시 폴더>`로 먼저 내보낸 뒤 같은 폴더를 `--check --out <임시 폴더>`로 확인한다 |
| JSON → SO | Unity 에디터 임포터 | §3 표. JSON은 `com.unity.nuget.newtonsoft-json` 패키지로 읽는다 (Unity 공식 패키지, 외부 DLL 없음) |
| 검사 | 임포터 | §5. 실패하면 SO를 하나도 쓰지 않고 중단 |

JSON을 `Assets/` 밖(`DarkLegion/DesignData/`)에 두는 이유: Unity가 TextAsset과 `.meta`를 만들지 않게 하고, 빌드에 JSON이 들어가지 않게 한다. 빌드에는 SO만 들어간다.

## 2. 내보내기 규칙 (`export_game_data.py`)

| 항목 | 규칙 |
|---|---|
| 파일 | §3 표에 있는 시트만 내보낸다. 파일 이름은 `<Sheet>.json`. 시트 이름이 겹치면 §3의 "JSON" 칸 이름을 쓴다 |
| 형식 | `{"source": "08_카드_데이터베이스.xlsx/Cards_Master", "rows": [ {열이름: 값, …}, … ]}`. 행 순서와 열 순서는 시트 그대로. UTF-8, 들여쓰기 2칸, 파일 끝 줄바꿈 1개 |
| 열 이름 | 1행 머리글 그대로. 한글 머리글(`카드명` 등)도 그대로 쓰고, SO 필드 이름은 §3에서 바꾼다 |
| 숫자 | 정수는 정수, 소수는 소수. Excel 백분율 문자열 `"14%"`는 `0.14`로 바꾼다 |
| 빈 칸 | `null`. 대시 `—`·`-`도 `null` (Cards_Master의 Skill·Action HP 등). 임포터는 §3 "빈 칸" 규칙을 따른다 (대부분 0 또는 빈 문자열) |
| `Y`/`N` 칸 | `Exhaust`·`EnqueueTwice` 등은 `true`/`false`로 바꾼다 |
| `Lv1` 같은 레벨 | 숫자 `1`로 바꾼다 |
| 빈 행 | 첫 열(ID)이 비어 있으면 그 행에서 끝낸다. 그래서 시트 아래쪽의 설명 메모(예: Floor_Scale 계산식)는 내보내지 않는다 |
| 정수 소수 | `16.0`처럼 소수점 아래가 0인 숫자는 정수 `16`으로 쓴다 |

## 3. 시트 → SO 매핑

1단계 열의 ●는 1단계(1~2층 NEC, `31` §0)에서 임포터가 반드시 읽어야 하는 시트다. 1단계에서도 **모든 행을 내보내고 임포트한다**. 현행 해금·드롭 풀(`Cards_FloorUnlock`)만으로는 D-26의 1단계 카드 32장이 보장되지 않는다: 1~2층 드롭 풀에는 32장 밖의 카드 18장이 있고, 그 재료로 융합 결과 10장이 더 나올 수 있다. 그래서 1단계 빌드는 카드 보상·이벤트 카드 후보를 1단계 32장(`Stage1CardPool`)과의 교집합으로 제한한다 (`01` D-44). 데이터는 그대로 두고 2단계에서 제한을 끈다. 적 11종은 층 구성으로 정해진다.

## 4. 카드 강화값 `Up_Params` (D-31·D-40)

`Cards_Upgrade`의 Before/After는 사람이 읽는 문구라 형식이 카드마다 다르다. 엔진은 **Up_Params**만 읽는다.

| Upgrade_Type | Up_Params 형식 | 예 |
|---|---|---|
| 몬스터 Value+ | `HP=n;ATK=n;DEF=n` (강화 후 절대값) | `NEC_MON_001` → `HP=12;ATK=3;DEF=1` |
| Cost- | `Cost=n` (강화 후 비용) | `NEC_SKL_002` → `Cost=0` |
| Skill·Action Value+·Effect+ | `ResolverSpec Params 키=강화 후 값` 하나 (`10_카드_런타임_매핑_상세.md` §3·§4의 키) | `NEC_ACT_004` → `Damage=19`, `NEC_ACT_003` → `DamageMult=1.2` |

새로 생긴 Params 키 (`10` §4에 없던 것): `TokenHp`(소환 토큰 HP), `DamageMult`(합산 피해 배율), `ExtraAttackDamage`(추가 공격의 피해 보너스). 리졸버는 강화된 카드일 때 Up_Params의 키 값으로 기본 Params를 덮어쓴다.

`check_design.py` R16이 확인한다: 몬스터의 Before = Cards_Master, Up_Params = After, Cost-는 비용이 줄었는지, 나머지는 Up_Params 값이 After 문구에 있는지.

## 5. 임포터 검사 (`05` §11 구체화)

| 검사 | 실패 조건 |
|---|---|
| 중복 ID | §3 "키"가 같은 행이 두 개 이상 |
| 잘못된 참조 | Card_ID·MON_ID·ENE_ID·Relic_ID·Status_ID가 가리키는 행이 없음 (Fusion_Recipes 재료·결과, Monsters_Master.Card_ID, Boss_List.ENE_ID·BossRelic_ID, Reward_EliteRelic 풀 등) |
| 비용·수치 범위 | Cost < 0, HP ≤ 0(몬스터·적), 확률 행 합 ≠ 1(Reward_BattleTable, Event_FloorPool 각 층) |
| 동작 핸들러 없음 | 1단계 범위 카드 32장의 ResolverKey, 1단계 저주 카드 3장(CUR_002·003·004, `01` D-45), 1단계 유물·이벤트 7종의 핸들러가 코드에 등록되어 있지 않음 (§6) |
| Up_Params 형식 | `Key=Value;…`로 읽히지 않음 |
| Position_Bonus | §5.1 규칙에 맞지 않는 Bonus_Type·Value |
| Localization | MVP는 검사하지 않는다 (D-41) |

검사가 하나라도 실패하면 기존 SO를 그대로 두고 콘솔에 실패 목록을 출력한다. 사라진 ID의 SO는 지우지 않고 경고만 한다 (`31` #17).

### 5.1 Position_Bonus Value 해석

`04` Position_Bonus의 Value는 `+1`, `+10%`, `없음`처럼 형식이 섞인 문자열이라 JSON에도 문자열로 나간다. 임포터는 **Bonus_Type을 먼저 보고** 아래처럼 해석한다. Excel 스키마는 바꾸지 않는다.

| Bonus_Type | Value 형식 | SO 값 | 예 |
|---|---|---|---|
| `null` (Excel `—`) | 무엇이든 무시 | 보너스 없음 | Middle `없음` |
| `DEF_Flat` | `+N` (정수) | DEF 가산 N | Front `+1` → 1 |
| `Skill_Amp` | `+N%` | 효과 배율 가산 N/100 | Back `+10%` → 0.10 |
| 그 밖의 값 | — | **임포트 실패** (§5) | — |

부호 `+`가 없거나, `DEF_Flat`에 `%`가 붙거나, `Skill_Amp`에 `%`가 없으면 임포트 실패다. 이 세 행은 임포터 단위 테스트의 기대값으로 손으로 적는다 (`32` §11.2).

## 6. 문구만 있는 데이터의 동작

몬스터 효과 칸·유물 Effect·이벤트 Result는 문장이다. 임포터는 문장을 해석하지 않는다. 동작은 ID로 찾는 코드 핸들러가 맡는다.

| 데이터 | 동작 정본 | 핸들러 키 |
|---|---|---|
| 카드 (Skill·Action) | `10_카드_런타임_매핑_상세.md` §3·§4 ResolverSpec | ResolverKey (`10` §5 자동 규칙) |
| 몬스터 효과 | `17_카드_데이터베이스.md` 카드별 효과, `09` Monsters_Master 분류(D-25) | Card_ID |
| 유물 | `24_콘텐츠_런타임_상세.md` §1 (20종) | Relic_ID |
| 이벤트 | `24` §2 (8종), 화면 문구 #33 | Event_ID + Option |

SO에는 화면에 보여 줄 문구와 핸들러 키만 담는다. 효과 수치를 바꿀 때는 Excel과 해당 MD를 같은 PR에서 고친다 (game-design 스킬 §3).
