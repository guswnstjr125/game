## 1. 공통 원칙

- 모든 결과는 **BattleAction → Queue** (`06_전투_코어_상세설계.md` Rule 1~4)
- Main Phase에서만 플레이어가 Sacrifice/Fusion **요청**
- `Soulbound` 몬스터: 희생 **불가** (Validator 거부)
- `IsDead` 유닛: 희생·융합 재료 **불가**

## 2. SacrificeSystem

### 2.1 클래스 구조

```csharp
public class SacrificeSystem
{
    public SacrificeRequest CreateRequest(RuntimeMonster target, BattleContext ctx);
    public SacrificeValidationResult Validate(SacrificeRequest req);
    public void Execute(SacrificeRequest req); // BattleAction만 Enqueue
}

public class SacrificeRequest
{
    public RuntimeMonster Target;
    public RuntimePlayer Player;
    public int ExpectedCrystal;
}

public class SacrificeValidationResult
{
    public bool IsValid;
    public string ErrorCode; // SOULBOUND, NOT_ALLY, DEAD, PHASE_LOCKED, ...
}
```

### 2.2 희생 흐름 (의사코드)

```
PlayRequest (Main Phase)
→ SacrificeValidator.Validate(target)
→ Target Lock (희생 예약, 즉시 슬롯 제거 금지)
→ Enqueue SacrificeAction
→ [Queue] SacrificeAction.Execute
    → GainCrystalAction (Lv1:+1, Lv2:+2, Lv3:+3, 파편:+1, 수정골렘 Lv2:+3; 유물 보너스는 턴당 첫 희생만 — `01` D-04·D-15)
    → OnSacrifice Trigger (TriggerBus, Priority.On)
    → IsDead = true → Death Queue
→ Flush Death → Flush Trigger
→ 소스 Monster 카드 → DiscardPile (`04_시스템_설계.md`: 몬스터 사망 시 카드 Discard)
```

### 2.3 Crystal 지급 (`16_밸런스_규칙.md`)

| 대상 | Crystal |
|------|---------|
| Lv1 | +1 |
| Lv2 | +2 |
| Lv3 | +3 |
| 수정 골렘 파편 (MON_NEU_L1_001) | +1 (0코스트 제물, `01` D-04) |
| 수정 골렘 Lv2 | +3 (일반 Lv2 +1 추가) |

### 2.4 OnSacrifice 시점

`SacrificeAction.Execute` 내 **Crystal 지급 직후**, Death Queue 등록 **이전**.

### 2.5 에러·롤백

| ErrorCode | 처리 |
|-----------|------|
| INVALID_PHASE | 요청 거부, UI 토스트 |
| SOULBOUND | 거부 |
| TARGET_DEAD | Resolve 시 Skip (타겟 재검증) |
| QUEUE_OVERFLOW | EmergencyCleanup |

롤백: Validation 실패 시 **Lock 해제만**; Queue 진입 후에는 Death 파이프라인 완료까지 진행.

## 3. FusionSystem

### 3.1 클래스 구조

```csharp
public class FusionSystem
{
    public FusionRequest CreateRequest(RuntimeCard a, RuntimeCard b, BattleContext ctx);
    public FusionValidationResult Validate(FusionRequest req);
    public void Execute(FusionRequest req);
}

public class FusionResolver
{
    public MonsterData Resolve(FusionRequest req, BattleRandom random);
}
```

### 3.2 융합 조건

> 정본: `01_MVP_설계_동결_선언.md` §7 **D-03**

- 전투 중 Main Phase, **손패**의 같은 **Monster 레벨** 카드 2장 (필드 유닛·토큰 불가)
- 맵 진행: **3스테이지마다** = 노드 3·6·9 클리어 시 **FusionCharge +1** (최대 3, 층 이동 시 유지). 융합 1회 = 충전 1
- 비용: Lv1+Lv1 Crystal 2 / Lv2+Lv2 Crystal 3 / Lv3+Lv3 불가 (`LEVEL_CAP`)
- 재료 2장 **영구 소멸** (ExhaustPile 아님 — DeadCard)
- 결과: 새 Monster 카드 1장 생성 → 손패 (이후 덱 영구 편입)

### 3.3 Resolve 알고리즘

```
1. FusionRecipeRegistry.TryGetFixed(materialA, materialB) → 있으면 100% Fixed (A·B 순서 무관)
2. else Random:
   - 같은 클래스: 80% 클래스 Lv+1, 20% NEU Lv+1 (Mutation은 MVP 비활성)
   - NEU + 클래스: 50% / 50%
   - 서로 다른 클래스: 50% A 클래스 / 50% B 클래스
   - 개별 결과: Fusion_RandomPool Weight 비례 (Lv1 풀은 클래스 80 / NEU 20, Lv2→Lv3은 클래스 100. `01` D-21)
3. RuntimeFactory.CreateCard(resultMonsterData)
4. Enqueue MoveCardAction (소재 2장 제거) + AddCardAction
```

레시피表: `09_몬스터_바이블.xlsx` → Fusion_Recipes (FUS_001~013)

### 3.4 실패 케이스

- 레벨 불일치 / Soulbound / 전투 중 아님 / FusionCharge 0 / Crystal 부족 / Lv3+Lv3(`LEVEL_CAP`) → Validate 실패
- 결과 풀 비어 있음 → Fallback Lv+1 랜덤 Common

## 4. CardResolver 연동

희생·융합은 **카드 Play가 아닌** 별도 Command → 전용 Action 생성.

```
BattleViewModel.RequestSacrifice(monsterUnitId)
→ SacrificeSystem.Execute

BattleViewModel.RequestFusion(cardIdA, cardIdB)
→ FusionSystem.Execute
```
